# Frontend design

Use only for interface design, redesign, frontend development involving an interface, and webpage SEO or sharing previews. Read the relevant sections; do not read for backend-only, data, documentation, or other unrelated tasks. This file is the single detailed source of design preferences; do not duplicate it in the three design skills.

## Skill responsibilities

- For new pages, prefer `finesse-ui`: first clarify the page purpose, desired style, and unwanted effects; briefly describe the design direction and implement after confirmation. Prefer localized adjustments for subsequent feedback.
- For redesigning existing pages, prefer the Taste suite's `redesign-existing-projects` (directory `redesign-skill`): first confirm what to retain, the target style, and the scope, then adjust layout, motion, and information density while preserving functionality not requested to change.
- After implementation, use `impeccable audit`, then apply `polish` as needed for actual issues. An audit does not authorize changes; avoid repeated audits or endless polishing.
- These are default responsibilities, not a pipeline requiring all three skills every time. Read only the skills and references needed for the current stage. Explicit user choices, existing project design systems, and the scope of localized changes take precedence; do not mechanically stack conflicting style rules.

Skill sources: [finesse-ui](https://github.com/mouse-lin/finesse-skill), [redesign-existing-projects](https://github.com/Leonxlnx/taste-skill), and [impeccable](https://github.com/pbakaus/impeccable). Prepare the actual execution environment using each author's current installation instructions. These rules neither replace the skills' full text nor establish that they are installed.

## Information density

- Keep desktop and mobile interfaces as compact as practical: first tighten the page's whitespace, padding, margins, line heights, module sizes, and repetitive explanations. Increase information density while preserving readable text, clear hierarchy, and reliable click and touch targets. Keep similar modules consistent in size and spacing.
- Compact does not mean collapsing content or hiding it behind buttons. Optimize the default visible page first; decide whether to hide secondary content based on purpose, frequency of use, and importance. Keep core information and primary actions directly visible.
- Identify the page's core content and put it in the default first viewport. Chart pages should show an actual chart; titles, status, entrances, tabs, filters, and explanations must not fill the first screen. Prioritize content on desktop too, with stricter mobile constraints. Keep only the prerequisite information and compact frequent controls needed to understand the content; place the rest after it or in the appropriate work area. Verify actual content placement in common phone viewports; a chart entrance is not evidence that the chart is visible.
- App-style navigation does not replace compact design within sections. Tighten settings, filters, tables, options, and empty states as well. Avoid stacking padding, margins, and large empty cards to achieve touch-target height; verify visual dimensions and interaction areas together.
- Remove desktop minimum heights that serve no purpose from mobile summaries, lists, and empty states; let real content set the height. Short summaries must not fill oversized cards, and long ones must not be squeezed into narrow columns. Use compact text for dates, retention periods, and counts rather than presenting them as large buttons.
- Use consistent compact dimensions for ordinary buttons, inputs, and selectors. Inputs for short values such as symbols should not inherit large quote-title typography. Check the actual height and surrounding whitespace of selected, disabled, and unselected controls, not just their containers. Also check line spacing, label/value gaps, and container whitespace in legends, zoom sliders, and indicator summaries so auxiliary information does not consume more space than the content.
- Organize card metadata into stable logical rows; statistics can divide the available width equally. Omit repetitive text when a compact brand graphic conveys its meaning, retaining a complete accessible name. Verify one-line and multiline labels, three-digit selected values, and the longest option; inspect computed dimensions and combined parent/child spacing rather than only new CSS values.
- In calendars and matrices with fixed columns, test the longest real entries. Keep group headings on one line, truncating when necessary while preserving full accessible names. Task text and status may wrap naturally and determine row height, with date cells matching it; fixed heights must not squeeze out or obscure status. Prefer 16px text in mobile inputs and native selects; tighten control height and padding to avoid iOS focus zoom.
- Tables and matrices should first fill the available width. Size columns for the longest real labels, units, and a reasonable number of digits. Sparse content may narrow further before horizontal scrolling is needed; do not reserve large empty areas for extreme values. Confine necessary scrolling to the table. In dense security lists, place symbols before names, give the symbol column a consistent width accommodating actual market formats, and align names and subsequent content by column. Place row totals near their names and corresponding visual bars, visually separated from daily or weekly values.
- When dense lists use single-line tags, expose overflow within that row rather than wrapping and increasing item height. Support direct horizontal viewing by touch; hover scrolling should apply only to tags that actually overflow. Keep right-side values and actions visible, and retain access to complete tags.

## Design mobile around app-like workflows

- Identify the most frequent mobile activities before organizing the first screen, navigation, and action paths. Reorganize content for the available mobile space rather than merely stacking desktop columns into a long page or scaling them down.
- Bottom navigation is itself navigation: group it by main business content or frequent actions. Do not give infrequent explanations or duplicate directories their own tab. A bottom bar plus a few short in-group switches can provide navigation; place secondary guides after content or initially collapse them, without inventing work areas to fill the bar. Remove duplicate entrances in mobile content or the upper-right corner when the bottom bar already provides them.
- Related pages may share mobile bottom navigation with continuous entrance order, names, icons, and selected states. Preserve each page's real URL, use links for cross-page entrances, and name them by business content rather than internal identifiers such as Model1.
- Keep guidance essential to getting started or switching to the user's own data, such as uploading trade records, prominent. Preserve initially expanded guidance; the user may explicitly collapse it into a small entrance above the bottom bar and reopen it. A compact redesign must not leave only an obscure corner button.
- Use second-level menus only for genuinely infrequent or secondary functions. Entrance names must suggest their content; assess the loss of discoverability from deeper paths. Core content should be directly accessible. Do not automatically add independent topic pages as primary-tool functions or force bottom navigation onto them.
- Prefer continuous scrolling within one work area for short related content that benefits from consecutive reading; do not add second-level tabs merely to separate two sections. After removing language- or permission-specific entrances, navigation must still be useful to other users. Test actual combinations of visible entrances, allowing an independent narrow icon item when necessary while keeping bar height and visual language consistent.
- On market-data pages, prioritize the current instrument, key values, common switches, and charts. Give management, settings, and infrequent explanations clear work areas according to their purpose. Use bottom navigation only when content and frequency justify it; do not mechanically reuse identical tabs or hide primary functionality.
- Make frequent switching directly usable on narrow screens. For a small number of instruments, equal-width symbol buttons may be used, with names, prices, and status grouped in the current instrument's details rather than repeated as large blocks in every switch item. Test the actual maximum count, not just one item.
- Shorten mobile wording according to the action's purpose. Filter entrances, periods, and tags need not repeat all desktop wording. Preserve business meaning, current selection, and necessary explanation; full names must remain available in expanded content or accessible names. Prefer a shared row for a small number of filters; expanded menus may be wider without squeezing their options.
- Give filters at the same level consistent selector behavior, showing category, current value, and an expansion arrow. Combine chart/table display modes into one selector rather than two page tabs alongside period and market selectors. Bottom navigation may use short names; keep full business names in content headings to avoid changing content identity.
- Place mobile news thumbnails beside their text, usually text on the left and image on the right, aligned with the top of the time/tag row rather than leaving an empty row above the image. Items without images use the full row. Test short text, long text, and tall images; do not place a small image alone beneath text with large whitespace. Preserve image-viewing entrances.
- Prefer recognizable short names in the current language for mobile shortcuts, leaving internal codes in details or data contracts. Short names must identify real objects; do not rename a composite index as another index or a futures contract merely for familiarity. Document links may shorten the visible path while retaining the full URL, fragment, and content.
- First identify the scope the user wants to borrow from a reference screenshot. If it concerns axis typography only, adjust that portion only; do not also replace layout, brand, or content structure without a request. Preserve hierarchy and identifying features when compressing explanations.
- Preserve the desktop version's brand, fonts, colors, control language, and business meaning. Mobile may change content order, navigation, and action placement while maintaining selection and state continuity. A mobile-only redesign must not change desktop layout or data logic.
- At realistic narrow-screen sizes, verify core actions, long names, maximum list counts, empty states, loading/errors, scrolling, and fixed-bar occlusion. Do not claim interactions pass based only on CSS or screenshots. Also check desktop to confirm mobile changes do not spill over.
- When mobile has a separate list work area, reassess visible item counts for the reading purpose rather than inheriting desktop layout limits. Distinguish source counts, frontend filtering, and display limits; preserve existing sorting and filtering criteria. Handle necessary source changes according to consumer contracts.
- Recheck actual loading behavior during mobile redesigns: CSS hiding does not defer requests or parsing. Inspect requests on first view and work-area changes, loading of offscreen content on demand, compression, and caching. Distinguish transferred bytes, decompressed size, and runtime overhead; smaller files do not prove shorter loading times. Separately check consumer contracts when changing production data projections or generators.
- Reuse existing task tabs for browser references and verification, and close tabs no longer needed from the current round after checking. Do not accumulate test pages or close tabs the user or another task is using.
- Turn recurring user corrections into executable checks in this file as they are fixed; record page-specific behavior in project specifications. Proactively check these issues on other pages. Record actual feedback and verification conclusions rather than expanding each fix into a repetitive experience list.

## Shared interaction language and chart space

- Header, footer, sidebar, and mobile bottom navigation belong to one design language. When changing shared components, check all actual consumers, not just the current page. Set bottom-bar entrances for actual primary content without filling a quota. Unify bar height, safe areas, icon sizes, labels, selected states, and control styles. Reuse one definition for synonymous icons; pages configure entrances and behavior rather than redrawing them or overriding dimensions.
- Recheck mobile sidebar/drawer density: tighten brand areas, group spacing, menu rows, and account areas separately. Let menu content scroll independently, with close controls and the last item reachable; do not merely scale down the desktop sidebar.
- Use different icons for different meanings within one bottom bar; reuse the same definitions for synonymous entrances across pages. Distinguish content themes from tool actions: AI-industry news needs a recognizable AI theme; a generic newspaper cannot distinguish its category, and an AI-assistant/generation icon is unsuitable for industry news. Prefer clear business imagery over plain text or meaningless decorations.
- When desktop already has an appropriate business SVG, reuse its source for the mobile entrance, adapting only size and stroke presentation rather than replacing it with another image of the same meaning. Verify actual desktop/mobile entrances and other icons in the same bar.
- For stock markets associated with a country, country-feature elements such as stars, stripes, and circles may be combined with business imagery such as candlesticks, retaining a short market name. Distinguish such composites from official flags. Decorative candlesticks in stock entrances should rise toward the upper right.
- Check icon silhouettes and visual weight at actual phone sizes; avoid packing symbols into an image users must decipher. Slightly enlarge elements with small filled areas, such as stars. Calibrate size, strokes, image/text baselines, and selected backgrounds visually rather than merely giving SVGs equal width and height. Preserve familiar brand imagery such as X while integrating its bottom-bar dimensions, colors, and selected state so it does not stand out.
- Verify officially specified marks such as national flags against authoritative designs for proportions, element counts, placement, and orientation. Preserve the complete design when scaling; do not reduce a five-star flag to an approximate single-star mark. Colors must follow the interface's SVG language. Monochrome marks inherit `currentColor` and selected states while retaining the correct design; official color presentations use authoritative colors.
- Reuse existing visual styles for tabs at the same level within a project, prioritizing styles the user explicitly preserves. Distinguish selection, anchor navigation, and keyboard focus. Content navigation must not enclose large content areas in heavy borders or outward circles; retain clear, subtle keyboard-focus cues.
- Preserve the same brand-mark silhouette when scaling for mobile and desktop. Scale corner radii with the mark instead of keeping a fixed value that makes small marks rounder.
- In app-style layouts, let content scroll between fixed top and bottom work areas without scrollbars covering navigation. The last item must be reachable and work-area changes must preserve business state. Avoid nested containers blocking vertical scrolling; horizontal chart actions must not lock page scrolling.
- Horizontal tag bars may use small edge arrows to indicate and advance overflow, hiding space-consuming horizontal scrollbars. Show arrows according to available scroll direction and automatically reveal the selected item; retain touch swiping, mouse dragging, and keyboard operation. Do not mechanically apply this to charts or matrices that need a scrollbar for positioning.
- If horizontal switching or sidebar filtering already exists, first adapt that mechanism for mobile. Do not stack another horizontal scrolling layer or turn filtering into a separate full page. Hiding a duplicate scrollbar only changes its visibility, not horizontal scrolling or single-line tags into wrapped tags. Preserve navigation and interactions the user requests; record specific default open/closed states in page specifications.
- Whenever creating or changing a chart page, check typography and whitespace on both axis sides. Use smaller tick and price-label typography and tighten axis width to actual labels instead of fixed large margins. Verify the longest numbers and unclipped edges. Omit useless trailing zeros in auxiliary ticks, retaining decimals needed for low prices or narrow ranges; display rounding must not alter actual quotes or structured-data precision.
- Keep chart borders and axes in the viewport while historical content pans within the plot. Reassess chart height for the phone's visible space and reading purpose rather than inheriting a fixed desktop height. Give auxiliary volume plots a smaller share of space, prioritizing the main chart; do not confuse independent analytical subplots with volume.
- Horizontally scrollable or pannable charts and matrices must support both touch and mouse dragging, including mouse input at phone viewport sizes. Separate dragging from clicking, preserve vertical page scrolling, and verify both input types. Retain keyboard, wheel, and scrollbar operation according to the component's purpose.
- Design chart hover details for mobile too: small typography, short labels, compact line spacing and padding, and no repetitive headings or long explanations, while retaining dates, units, and key-value precision. Verify width and placement with touch and pointer input. Keep popovers inside the visible chart/content area without covering fixed navigation or most of the main plot; desktop may retain fuller wording.
- Reserve moderately sized fixed widths for chart-header time and dynamic values based on actual digit counts, using tabular figures to prevent movement as values change during dragging or refresh. Check both maximum and zero values; do not buy stability with excessive padding. Remove repeated nested borders and padding that narrow the plot, giving related charts consistent usable widths. Non-trading intervals with no data changes may become narrow gray separators while retaining session boundaries.

## Webpage SEO and sharing previews (on demand)

- When creating public pages or changing indexable content, routes, initial HTML, head, or share cards, read [public-page-seo-assist](https://github.com/tsetsugekka/codex-sakura-account-site-skills/blob/main/skills/public-page-seo-assist/SKILL.md) and references relevant to the current issue. Do not repeat the SEO workflow for localized visual changes that leave these contracts intact. The skill owns detailed methods; this file retains page-production triggers and acceptance criteria.
- First confirm the public/indexable scope and the actual content the user wants searchable. Initial responses for articles, reports, and rankings must contain the agreed relevant content, not just a product description; chart and calculation tools need not embed their entire history. Use the project's appropriate generation, content-update, or server-rendering process, preserving the authoritative source and ownership of initial and interactive content. Do not substitute `noscript` for delivery verification, lose content on JS mounting, or show duplicate content.
- Emit charset, a unique title, description, canonical, OG/Twitter, and appropriate robots in the initial head before application and analytics scripts; place charset near its start. Align canonical and `og:url` with the final route and sitemap `loc` when listed. Follow project language and favicon conventions; structured data must match the real page type rather than treating data tools as articles.
- Distinguish quote/data timestamps from genuine publication times. Set sitemap `lastmod` only when the project permits it and the time of a significant content change is known; otherwise omit it. Deployment or cron wakeups are not content changes. Test first-visit data failure separately from refresh failure, retaining available valid snapshots under current freshness contracts with truthful status; do not invent data or remove generation validation.
- For protected pages, deliver only safe route-specific sharing metadata while preserving login, API authorization, and indexing policies. Share images must be representative public images with truthful dimensions, not private images or favicons; make text-card compatibility limitations clear. Preserve server-owned HTML markers and content through existing generation/publishing processes.
- Verify the initial response, JS-disabled view, normal DOM, direct detail URLs, built and live head, actual response statuses, and redirects. Perform live verification only for the published scope and record unpublished status truthfully. Inspect target-crawler responses and image metadata for sharing; actual messaging requires user authorization. Keep internal prompts, permissions, and operational notes out of public artifacts. Report local rendering, search results, and Search Console crawl/render evidence separately; tags, `noscript`, `site:`, or other search backends do not establish Google indexing.
