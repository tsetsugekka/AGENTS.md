# Frontend design

Use only for interface design, redesign, frontend development involving an interface, webpage loading and performance optimization, and SEO or sharing previews. Read the relevant sections; do not read for backend-only, data, documentation, or other unrelated tasks. This file is the single detailed source of design preferences; do not duplicate it in the three design skills. Execute SEO, sharing-preview, and performance checks directly from this document; installing corresponding skills is not required.

Keep only design principles and verification methods that transfer across projects. Project design documents or specifications own concrete business behavior, content sections, icon compositions, dimensions, and default states.

## Design judgment and reference review

- For design and redesign, first identify the users, core task, content that should appear in the first viewport, and styles the user has already accepted, then choose a skill. Do not apply an explainer, chat box, or back-office template just because the name includes Guide, SOP, AI, or workspace. When the requirements are sufficient, state your judgment and proceed; ask only about ambiguity that materially affects scope.
- When the user supplies visual references, actually view the key screenshots, illustrations, and pages. Identify their information hierarchy, content density, use of images, and interaction paths within the requested scope of reference. Reading the article text alone does not establish an understanding of its interface references. State when something cannot be viewed rather than claiming to have compared it.
- On mixed pages, design the reading layout, explanatory diagrams, and interactive products separately. Use muted sections only where they suit the explanation; choose white backgrounds, vivid colors, photos, and icons according to content and branding. Do not treat preferences such as banning pure white, using one accent color, or seeking a premium look as universal constraints, or turn feedback on one page into a global color ban. Consistency comes from hierarchy, spacing, components, and meaning; independent products presented together may retain their own visual languages.
- Product comparisons should use a complete task readers can immediately understand, with comparable content richness and completeness on both sides. High-fidelity demos need recognizable inputs, actions, feedback, and continuous state, rather than only text cards or screenshots; accurately label the scope of simulation. AI entry points should show recommendation reasons, choices, generated results, and ways to adjust them as the task requires. Do not reduce AI-native to an empty input box. Provide direct switching for comparisons spanning multiple screens while retaining the normal interaction path.
- Complete representative working interfaces and key interactions before creating banners or covers from them. Keep the accepted direction and compare actual desktop and mobile renders against the references and user goals, checking first-screen appeal, content density, recognizable controls, and key states. Audit scores or passing style rules cannot replace this check. Distinguish unverified work from work awaiting the user's aesthetic assessment without repeatedly waiting for design approval.

## Skill responsibilities

- For new pages, prefer `finesse-ui`: briefly describe the direction based on the judgment above and implement it. Prefer localized adjustments for subsequent feedback; reassess the direction when the user requests a complete redesign.
- For redesigning existing pages, prefer the Taste suite's `redesign-existing-projects` (directory `redesign-skill`): first confirm what to retain, the target style, and the scope, then adjust layout, motion, and information density while preserving functionality not requested to change.
- After implementation, use `impeccable audit`, then apply `polish` as needed for actual issues. An audit does not authorize changes; avoid repeated audits or endless polishing.
- These are default responsibilities, not a pipeline requiring all three skills every time. Read only the skills and references needed for the current stage. Explicit user choices, existing project design systems, and the scope of localized changes take precedence; do not mechanically stack conflicting style rules.

Skill sources: [finesse-ui](https://github.com/mouse-lin/finesse-skill), [redesign-existing-projects](https://github.com/Leonxlnx/taste-skill), and [impeccable](https://github.com/pbakaus/impeccable). Prepare the actual execution environment using each author's current installation instructions. These rules neither replace the skills' full text nor establish that they are installed.

## Infographics for explanatory pages (on demand)

Use this approach only when a page or section primarily explains how something works, steps and feedback, architecture, scope, or comparisons between objects, and a diagram is easier to understand than a short passage. Do not apply it by default to articles, forms, queries, data browsing, or ordinary operating areas; use it only in suitable explanatory sections of mixed pages. Project branding, existing design systems, and user-specified styles take precedence. Do not make this the default appearance of every webpage.

- First check actual records to confirm the real workflow's starting point, sequence, object mappings, and output formats, then choose a flow, branching or merging diagram, loop, matrix, coordinate plot, or nested diagram for the relationships the reader needs to understand. Do not invent one-to-one mappings or change causality to make the layout tidy. Keep simple explanations as short prose or lists. Do not force different relationships into the same kind of card; equally sized cards suit genuinely parallel, independent items. Do not prescribe a number of layout types merely for variety.
- Borrow how examples express relationships, without combining the appearances of different versions. Use a consistent visual language for the page's canvas, line meanings, cards, captions, and labels; redraw relationships borrowed from other examples in the page's style. Nodes need not all have the same color or frame.
- Before adding columns, check the host page's existing navigation, sidebar, and available content width. Fit explanatory sections into that structure rather than copying an example's outer layout and squeezing the content. Do not impose a universal column count.
- Support key stages with small interfaces, illustrations, or SVGs that explain an action or object. Do more than swap icons beside long passages, but do not force illustrations into every section. Combine real text with CSS or SVG, preserving accessible reading order and necessary explanations. Do not turn the whole page into a hard-to-read, unsearchable bitmap. Long examples on explanatory pages may use a structural overview and excerpts; make omissions clear while retaining core capabilities and necessary relationships. Link to complete material only when it actually exists.
- Distinguish examples from actual steps or rules consistently across the page, directly on the elements concerned and through more than color alone, including example interfaces embedded in workflows. Permission to use fictional examples does not authorize inferring the real workflow. Prefer placing line meanings and item labels nearby; do not compensate for unclear identification with lengthy explanations or repetitive legends. Retain necessary facts, accessible explanations, and legends for shared line conventions.
- When a lightweight explanation fits, use clear text hierarchy, muted sections, and appropriate space. Colors, shapes, and line styles carry consistent meanings; do not distinguish things by color alone. Size, fill, position, and nesting may express degree, proportion, or containment, but must remain faithful to the source. Label qualitative illustrations explicitly; do not invent precise numbers or imply unverified quantitative differences.
- Connect arrows to the objects they actually affect. Distinguish feedback, returns, and optional relationships from the main flow; return arrows point to the actual step, with conditions and labels near the relevant branch or line segment. A tree trunk ends at its final branch, and merging lines reach the target node. Do not leave lines floating, crossing text, or extending unnecessarily. Share a trunk only for genuinely shared relationships; crossings or partial overlaps must leave each route distinguishable. Do not combine different relationships, such as the main flow and a return, into an undifferentiated line or imply merging or sharing that does not exist. Unrelated nodes must not obscure line endpoints; route returns around obstacles according to the actual layout. Use text for line labels, without additional small arrows or return icons that could be confused with directional lines.
- Reorganize diagrams for phones rather than shrinking the desktop version. Choose vertical flows, side loops, trees, or other narrow-screen structures according to the relationship, preserving direction, ownership, and conditions. Legends and secondary graphics may become more compact, but retain facts needed for understanding. When two-dimensional comparison is necessary, retain the matrix with accessible local scrolling rather than forcing it into a list that loses the comparison.
- Break captions at semantic boundaries, avoiding isolated characters and hard-to-read centered multiline text. Keep captions clearly aligned with the diagram on narrow screens. Align corresponding headings, explanations, values, and labels across parallel columns; when headings or subtitles take different numbers of lines, also check the corresponding starting positions of subsequent content. Size shared label columns for the longest real label and the available text space, without squeezing the body text for alignment. Do not prescribe a CSS technique.
- Render at actual desktop and narrow-screen sizes and at intermediate widths that change the arrangement, confirming that the effective viewport reaches the target size. Check every diagram's line endpoints, occlusion, overlap, labels, alignment, wrapping, overflow, and readability. Recalculate lines that depend on element positions when the layout changes and after hidden panels become visible. Verify each tab or view actually affected by this redesign or shared components, rather than only the first. Use existing audit tools according to their actual capabilities and invocation, without assuming a universal command or fixed font-size threshold. Preserve facts, applicability conditions, and unverified status during redesigns.

When visual reference is needed or creating a skill for independent distribution, open and compare all three bundled web infographic examples, whatever language the target page uses: [Chinese](references/web-infographic.html), [Japanese](references/web-infographic.ja.html), and [English](references/web-infographic.en.html). The three versions are not translations of the same content; they differ in relationship types, layouts, palettes, and small interface illustrations, and complement one another: the Chinese version shows steps with feedback, branching and merging, and containment and scope; the Japanese version shows closed loops, role handoffs, and connections between layers; the English version shows an object × dimension matrix, a two-dimensional range, and where states go. Choose expressions from all three according to the relationships the page needs to explain, rather than looking only at the version in the page's language. Render them before borrowing their expressive techniques; do not copy layouts, content, or palettes. The principles above already provide the necessary web guidance; no separate static-flowchart skill is required, and its PPT, poster-size, or QR-code workflows are not imported. When publishing a skill, include this section and the required examples in the package, adjusting relative links.

## Information density

- Keep desktop and mobile interfaces as compact as practical from the first version: first reduce unnecessary whitespace, padding, margins, line heights, module sizes, and repetitive explanations, avoiding pointless nested frames. Do not achieve compactness by shrinking body text or text within diagrams. Keep text comfortably readable, hierarchy clear, click and touch targets reliable, and similar modules consistent in size and spacing.
- Compact does not mean collapsing content or hiding it behind buttons. Optimize the default visible page first; decide whether to hide secondary content based on purpose, frequency of use, and importance. Keep core information and primary actions directly visible.
- Identify the page's core content and put it in the default first viewport. Chart pages should show an actual chart; titles, status, entrances, tabs, filters, and explanations must not fill the first screen. Prioritize content on desktop too, with stricter mobile constraints. Keep only the prerequisite information and compact frequent controls needed to understand the content; place the rest after it or in the appropriate work area. Verify actual content placement in common phone viewports; a chart entrance is not evidence that the chart is visible.
- App-style navigation does not replace compact design within sections. Tighten settings, filters, tables, options, and empty states as well. Avoid stacking padding, margins, and large empty cards to achieve touch-target height; verify visual dimensions and interaction areas together.
- Remove desktop minimum heights that serve no purpose from mobile summaries, lists, and empty states; let real content set the height. Short summaries must not fill oversized cards, and long ones must not be squeezed into narrow columns. Use compact text for dates, retention periods, and counts rather than presenting them as large buttons.
- From the first version, give ordinary buttons, inputs, dropdowns, and date pickers compact dimensions that coordinate with adjacent controls; short-value inputs should not inherit oversized heading typography. Check computed height, minimum height, padding, line height, and accumulated parent/child spacing so shared styles or browser defaults do not inflate controls. Do not merely shrink containers or inspect declared CSS. Verify selected, disabled, and unselected states; preserve comfortable reading and reliable touch interaction rather than shrinking type to offset excess whitespace. Check line spacing, label/value gaps, and container whitespace in legends, sliders, and summaries so supporting information does not consume more space than core content.
- Organize card metadata into stable logical rows and group statistics by their reading relationships; divide width equally when comparison calls for it. Omit repetitive text when a graphic clearly conveys its meaning, retaining a complete accessible name. Verify short and long labels, realistic value ranges, and the longest options; inspect computed dimensions and combined parent/child spacing rather than only new CSS values. Reduce unnecessary wrapping in short phrases and labels through parallel wording, removal of repetition, and abbreviations supported by context. Do not force a single line by reducing font size, losing meaning, or truncating necessary content; recheck the starting positions of content within the same group afterward.
- Test fixed-column tables and matrices with the longest real entries. Choose wrapping or truncation according to the reading task, retaining access to complete content. Let real content determine multiline row height, keep cells within each row aligned, and do not obscure text or status with fixed heights. Prefer 16px text in mobile inputs and native selects; tighten control height and padding to avoid iOS focus zoom.
- Tables and matrices should first fill the available width. Size columns for the longest real labels, units, and a reasonable number of digits. Sparse content may narrow further before horizontal scrolling is needed; do not reserve large empty areas for extreme values. Confine necessary scrolling to the table. Align mixed-format identifiers, names, and values by column, choosing order and width for the identification task and actual content. Place aggregates near their labels and visual representations, visually separated from details.
- When dense lists use single-line tags, expose overflow within that row rather than wrapping and increasing item height. Support direct horizontal viewing by touch; hover scrolling should apply only to tags that actually overflow. Keep right-side values and actions visible, and retain access to complete tags.

## Design mobile around app-like workflows

- Identify the most frequent mobile activities before organizing the first screen, navigation, and action paths. Reorganize content for the available mobile space rather than merely stacking desktop columns into a long page or scaling them down.
- Choose navigation for the page purpose and frequent actions; do not require bottom navigation on every mobile page. When using a bottom bar, group actual primary content without splitting work areas to fill it. Check for unnecessary duplicate navigation across content, top, and bottom areas. Place secondary explanations in suitable context and keep core content and primary actions easy to discover.
- Related pages may share navigation with consistent ordering, names, icons, and selected states. Preserve each page’s real URL, use links for cross-page items, and name entries by user-understood content or actions rather than internal identifiers alone.
- Keep guidance essential to getting started prominent. If it can be collapsed, keep the entrance discoverable and allow reopening. Compact redesigns must not remove necessary guidance or change existing visibility agreements without authorization.
- Choose function hierarchy according to importance and frequency. Assess discoverability and interaction cost before deepening paths. Entrance names should indicate actual content, core tasks should be easy to reach, and compact layout alone should not justify extra menu levels or changing an independent page’s purpose.
- Short related content suited to consecutive reading may scroll within one work area; do not add second-level tabs merely to separate it. When navigation varies by language, permissions, or content state, check the usefulness, reachability, and layout of each actual visible combination.
- Make frequent switching directly usable on narrow screens. Choose buttons, tabs, or selectors according to the actual option count and label lengths. Keep only identification information in switch items and place details with the current selection, avoiding repetitive large blocks. Verify the real maximum option count, long labels, and first-screen occupancy, not just one item; supporting switch controls must not displace core content.
- Shorten mobile wording according to the action's purpose. Filter entrances, periods, and tags need not repeat all desktop wording. Preserve business meaning, current selection, and necessary explanation; full names must remain available in expanded content or accessible names. Prefer a shared row for a small number of filters; expanded menus may be wider without squeezing their options.
- Keep filters with the same level and purpose consistent, clearly showing category, current value, and expanded state. Choose filters, display-mode switches, or page navigation according to content hierarchy rather than duplicating a selection across multiple control sets. Short labels must still identify content accurately.
- Arrange mobile-list thumbnails and text according to their content relationship. Test short and long text, different image proportions, and imageless items; image placement should not create useless whitespace or squeeze text. Keep image-viewing entrances and complete text accessible, choosing alignment and left/right order for the page purpose.
- Use recognizable short names in the current language for mobile shortcuts, keeping necessary internal identifiers in details or data contracts. Abbreviations must not change the real object, purpose, or meaning. Link text may be shortened while retaining the complete destination, fragment, and content.
- First identify the scope the user wants to borrow from a reference screenshot. If it concerns axis typography only, adjust that portion only; do not also replace layout, brand, or content structure without a request. Preserve hierarchy and identifying features when compressing explanations.
- Preserve the desktop version's brand, fonts, colors, control language, and business meaning. Mobile may change content order, navigation, and action placement while maintaining selection and state continuity. A mobile-only redesign must not change desktop layout or data logic.
- At realistic narrow-screen sizes, verify core actions, long names, maximum list counts, empty states, loading/errors, scrolling, and fixed-bar occlusion. Do not claim interactions pass based only on CSS or screenshots. Also check desktop to confirm mobile changes do not spill over.
- When mobile has a separate list work area, reassess visible item counts for the reading purpose rather than inheriting desktop layout limits. Distinguish source counts, frontend filtering, and display limits; preserve existing sorting and filtering criteria. Handle necessary source changes according to consumer contracts.
- Recheck actual loading behavior during mobile redesigns: CSS hiding does not defer requests or parsing. Inspect requests on first view and work-area changes, loading of offscreen content on demand, compression, and caching. Distinguish transferred bytes, decompressed size, and runtime overhead; smaller files do not prove shorter loading times. Separately check consumer contracts when changing production data projections or generators.
- Reuse existing task tabs for browser references and verification, and close tabs no longer needed from the current round after checking. Do not accumulate test pages or close tabs the user or another task is using.
- Turn experience into general checks only when its applicability and verification evidence are clear and it transfers across projects. Record specific business behavior, icon compositions, content organization, values, and default states in project design documents or specifications. A single-page correction does not automatically become a global requirement; avoid repetitive experience lists.

## Shared interaction language and chart space

- Style every scrollbar to match the page's actual visual design.
- Style form controls such as dropdowns, inputs, and date pickers to match the page from the first version, just as with scrollbars. Coordinate typography, weight, colors, borders, corner radii, icons, dimensions, and spacing with adjacent components; do not design only their outer containers while leaving visually inconsistent default controls. Inputs and selection controls must be immediately recognizable. Check collapsed, expanded, input, selected, disabled, and error states, including density, readability, and occlusion in menus and calendar popovers. Preserve system-managed native selection interactions and customize the parts controlled by the page; styling must not impair control semantics, keyboard operation, or native mobile input capabilities.
- On both desktop and mobile, use dropdowns cautiously when there are few options. When the options can be laid out clearly, prefer segmented buttons, radio groups, or selectable chips as appropriate, keeping the options and current value directly visible and clickable; use navigation controls for switching work areas. Consider option count, label length, frequency of use, and available space together rather than adding an expansion step just to save space. Use a designed dropdown when there are many options, lengthy content, or a real space constraint, adding search when needed. Do not turn the preference for directly visible small option sets into a fixed numeric threshold.
- Header, footer, sidebar, and mobile bottom navigation belong to one design language. When changing shared components, check all actual consumers, not just the current page. Set bottom-bar entrances for actual primary content without filling a quota. Unify bar height, safe areas, icon sizes, labels, selected states, and control styles. Reuse one definition for synonymous icons; pages configure entrances and behavior rather than redrawing them or overriding dimensions.
- Recheck mobile sidebar/drawer density: tighten brand areas, group spacing, menu rows, and account areas separately. Let menu content scroll independently, with close controls and the last item reachable; do not merely scale down the desktop sidebar.
- Distinguish navigation-icon meanings by actual content or action, reusing one definition for synonymous entries. Use short labels for meanings that may be confused. Prioritize recognition over meaningless decoration; do not turn a project-specific icon composition into a universal template.
- When desktop already has an appropriate business SVG, reuse its source for the mobile entrance, adapting only size and stroke presentation rather than replacing it with another image of the same meaning. Verify actual desktop/mobile entrances and other icons in the same bar.
- Check icon silhouettes, recognition, and visual weight at actual display sizes; avoid stacking symbols that require guessing. Calibrate size, strokes, image/text baselines, and selected states visually rather than merely giving SVGs equal dimensions. Preserve recognizable brand imagery while coordinating navigation size, color, and state.
- Follow authoritative designs and permitted variants for formally specified marks. Interface adaptation must not arbitrarily change their proportions, patterns, or prescribed colors. Keep project-specific decorative graphics clearly distinguishable from official marks.
- Reuse existing visual styles for tabs at the same level within a project, prioritizing styles the user explicitly preserves. Distinguish selection, anchor navigation, and keyboard focus: show selection with a light background, text color, thin border, or small marker. Buttons, inputs, selects, and content areas must not gain heavy outlines, outward rounded frames, or double halos after mouse or touch interaction. Retain clear, restrained keyboard-focus cues rather than globally removing accessible focus.
- Do not call focus() unconditionally when updating part of the interface: refocusing after a mouse selection can trigger a large outer frame. Restore focus when needed to preserve keyboard position. Test actual mouse clicks, touch selections, Tab and arrow-key operation, and the state after rendering again, rather than only the default screenshot.
- Preserve the same brand-mark silhouette when scaling for mobile and desktop. Scale corner radii with the mark instead of keeping a fixed value that makes small marks rounder.
- In app-style layouts, let content scroll between fixed top and bottom work areas without scrollbars covering navigation. The last item must be reachable and work-area changes must preserve business state. Avoid nested containers blocking vertical scrolling; horizontal chart actions must not lock page scrolling.
- Make hidden items in overflowing horizontal tags or navigation discoverable and accessible, automatically revealing the selected item. Choose arrows, scrollbars, or other cues for the component’s purpose rather than requiring one style everywhere. Retain usable touch, pointer, and keyboard operations; hiding a scrollbar must not remove scrolling.
- First adapt existing switching, filtering, and scrolling mechanisms to mobile space, avoiding duplicate controls and unnecessary nested scrolling. Change navigation hierarchy or default open/closed states only according to page purpose and authorization, and update project specifications.
- When creating or changing charts, check axis typography and whitespace. Size axes and text for actual labels and readability, verifying the longest values and unclipped boundaries. Omit useless trailing zeros while preserving precision needed to distinguish small values or narrow ranges; display rounding must not change underlying data precision.
- Allocate space to axes, primary plots, and subplots according to chart purpose. Reassess mobile height for visible space and the reading task rather than inheriting a fixed desktop height. Supporting content must not crowd the primary analysis area, while independent analytical subplots retain space needed for understanding. Keep axes and boundaries readable during panning.
- Horizontally scrollable or pannable charts and matrices must support both touch and mouse dragging, including mouse input at phone viewport sizes. Separate dragging from clicking, preserve vertical page scrolling, and verify both input types. Retain keyboard, wheel, and scrollbar operation according to the component's purpose.
- Design chart hover details for mobile too: small typography, short labels, compact line spacing and padding, and no repetitive headings or long explanations, while retaining dates, units, and key-value precision. Verify width and placement with touch and pointer input. Keep popovers inside the visible chart/content area without covering fixed navigation or most of the main plot; desktop may retain fuller wording.
- Reserve moderately sized fixed widths for chart-header time and dynamic values based on actual digit counts, using tabular figures to prevent movement as values change during dragging or refresh. Check both maximum and zero values; do not buy stability with excessive padding. Remove repeated nested borders and padding that narrow the plot, giving related charts consistent usable widths.

## Webpage SEO and sharing previews (on demand)

- When creating public pages or changing indexable content, routes, initial HTML, head, or share cards, apply the checks in this section. Do not repeat the SEO workflow for localized visual changes that leave these contracts intact.
- First confirm the public/indexable scope and the actual content the user wants searchable. Initial responses for articles, reports, and rankings must contain the agreed relevant content, not just a product description; chart and calculation tools need not embed their entire history. Use the project's appropriate generation, content-update, or server-rendering process, preserving the authoritative source and ownership of initial and interactive content. Do not substitute `noscript` for delivery verification, lose content on JS mounting, or show duplicate content.
- Emit charset, a unique title, description, canonical, OG/Twitter, and appropriate robots in the initial head before application and analytics scripts; place charset near its start. Align canonical and `og:url` with the final route and sitemap `loc` when listed. Follow project language and favicon conventions; structured data must match the real page type rather than treating data tools as articles.
- Distinguish data timestamps from genuine publication times. Set sitemap `lastmod` only when the project permits it and the time of a significant content change is known; otherwise omit it. Deployment or cron wakeups are not content changes. Test first-visit data failure separately from refresh failure, retaining available valid snapshots under current freshness contracts with truthful status; do not invent data or remove generation validation.
- For protected pages, deliver only safe route-specific sharing metadata while preserving login, API authorization, and indexing policies. Share images must be representative public images with truthful dimensions, not private images or favicons; make text-card compatibility limitations clear. Preserve server-owned HTML markers and content through existing generation/publishing processes.
- Verify the initial response, JS-disabled view, normal DOM, direct detail URLs, built and live head, actual response statuses, and redirects. Perform live verification only for the published scope and record unpublished status truthfully. Inspect target-crawler responses and image metadata for sharing; actual messaging requires user authorization. Keep internal prompts, permissions, and operational notes out of public artifacts. Report local rendering, search results, and Search Console crawl/render evidence separately; tags, `noscript`, `site:`, or other search backends do not establish Google indexing.

## Webpage loading and performance (on demand)

- Read this section when creating pages, changing resource delivery, data loading or refresh behavior, or investigating sluggish pages; localized visual changes do not require another full audit. Distinguish audit-only, compression-only, and loading-structure changes without exceeding authorization. First read actual code, page specifications, and generation/publication procedures; preserve content, data meaning, and existing interactions.
- Measure transferred bytes and request counts separately for initial HTML, JS/CSS, business JSON/APIs, and third-party resources; check repeated requests during page/tab switching and continued use. Distinguish transfer size, decompressed size, parsing/rendering, and interaction time. State when authenticated loading or real-device performance is unmeasured; smaller files do not prove faster pages.
- Distinguish having gzip files from the browser actually using compression. Follow the real loading path to verify Content-Encoding, MIME, decoded content, and fallback to ordinary JSON; local compression estimates are not production results. Prioritize duplicate fetching, unused fields, compression, and revalidation of existing caches. Consider splitting or precomputation only for data still large after compression. Paging, compression, caching, and deferred loading are different measures; preserve freshness, authorization, and cache-isolation contracts.
- Lists should load only currently needed summaries that can be regenerated; details should read complete records identified by stable IDs, dates, or equivalent keys. Load unopened tabs, offscreen details, and history on demand rather than fetching everything on first visit. CSS hiding does not defer requests or parsing. Preserve initial content agreed for SEO; a public display window is not the retention period of original data.
- Coordinate data-format changes across writers, compressed copies, readers, and publication order. Validate new data before switching readers, reusing existing calculation, compression, and publication tools. Follow project authority, retention, and deployment rules; do not overwrite production data with old local copies or static deployment. Loading optimization does not authorize deleting history or expanding server retention.
- Use production builds and a browser to check desktop/mobile charts, menus, text, SVGs, dialogs, details, and loading/error states. Do not remove required styles or charts to reduce size. Prepare equivalent built styles before changing CSS delivery; keep the first screen and subsequent interactions usable.
- Compare before and after under the same measurement conditions. When publishing, remeasure actual responses, compression, and loading paths. Report transfer/request changes separately from loading/rendering/interaction changes, specifying measured scope and unverified aspects. Do not expand a redesign when actual improvement potential is small.
