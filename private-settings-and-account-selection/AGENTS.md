# Private settings and account selection (on demand)

Read only when a task needs accounts, sender identities, recipients, or other user-specific settings. These settings resolve known choices; they do not grant permission to send, publish, delete, or perform other new actions.

- Separate private settings from shareable rules. By default, maintain a short index at `private/SETTINGS.md` beside the main instruction file, linking to task-specific settings. Reuse an existing equivalent location and identify it in the entry point; do not load the entire private library by default.
- Record each setting's purpose, scope, confirmed values, source, and verification date. Account connection identifiers may be recorded, but passwords, keys, tokens, cookies, and other credentials remain under the official authentication process, not in private settings documents.
- The user's explicit instructions for the current task take precedence; otherwise follow the relevant private settings. Use a configured setting directly when it uniquely matches the current tool, rather than asking again merely because multiple accounts exist. Ask only when a setting is missing, genuinely ambiguous, invalid, or changes scope, and explain the specific reason.
- Before an external action, verify identity against the current tool's account information; an old connection ID is not permanently valid. When the ID changes but the full account uniquely matches, update the selection. Do not guess from similar display names or substitute editing sender fields for selecting the correct authenticated connection. If the original account is unavailable, do not silently switch accounts or recipients.
- Add or change persistent settings only when the user requests persistence; do not turn a one-time choice into a permanent preference. Reading or configuring settings does not mean an external action has occurred. If permission is denied, use the proper approval mechanism; if unavailable, report the limitation without bypassing it through another channel.
- Keep actual private files outside public repositories, skill installation directories, and automatic publication scopes, with access restricted to the user (typically directories `700` and files `600` on POSIX). Public versions provide only location conventions, rules, and necessary empty fields, not actual accounts, email addresses, connection IDs, personal paths, or completed configurations.
- Exclude actual private settings from publication and export through explicit file lists, checking the real commit or package contents. A directory named private or ignored by Git is not proof of safety. Read only fields needed for the current task; do not include unrelated private material in output, logs, or public artifacts.
