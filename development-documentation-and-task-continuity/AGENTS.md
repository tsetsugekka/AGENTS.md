# Development documentation and task continuity

- Development projects that need ongoing maintenance or cross-session handoff and involve multiple modules, external services or deployment, phased delivery, or complex business constraints should maintain the documentation responsibilities below; one-off small changes do not require the full set.
- Prefer existing documentation, naming, and directories. README covers purpose, entry points, and operations; SPEC covers current behavior, contracts, and acceptance criteria; CHANGELOG records important changes and release status; TASK records current tasks, unfinished work, blockers, and next steps; CASE-STUDY captures evidence, causes, fixes and their verification, and reusable lessons from real errors.
- Documentation may be a single Markdown file or indexed directories split by module or topic. When cases become numerous, use `case-study/` (or an existing equivalent), with one Markdown file per case and a directory README or existing index for navigation; do not invent cases when none exist.
- Read relevant documentation at the start of work and update only affected content when making changes; before ending, pausing, or handing off, write unfinished work back to the task entry point rather than leaving it only in chat.
- Maintain one authoritative source per fact or status and link to it elsewhere; distinguish current specifications, unimplemented plans, and historical records, as well as implementation, verification, publication, and runtime acceptance. Do not treat partial success as full completion.
- Documentation synchronization does not expand operational authority or permit credentials or internal records to enter public artifacts.
