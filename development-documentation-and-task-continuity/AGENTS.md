# Development Documentation and Task Continuity

- Maintain these five documentation responsibilities for development projects needing ongoing maintenance or cross-session handoff and involving multiple modules, external services or deployment, phased delivery, or complex business constraints. One-off small changes do not require the full set.
- Reuse existing files, naming, and directories. README covers purpose, entry points, configuration, and operating/build/verification/deployment commands; SPEC covers current behavior, contracts, constraints, and acceptance criteria; CHANGELOG records meaningful changes, impact, and release status; TASK records current scope, unfinished work, status, owners where needed, blockers, decisions, completion criteria, and next steps; CASE-STUDY records real failures with evidence, causes or labeled hypotheses, fixes, verification, and reusable lessons.
- Use a single Markdown file or indexed directories split by module or topic. For multiple cases, use `case-study/` (or an existing equivalent), one Markdown per case, with a directory README or existing index linking them. Do not invent cases when none exist.
- Read relevant documentation when starting or resuming; update affected content as requirements, implementation, or acceptance changes. Before ending, pausing, or handing off, write unfinished items and next steps back to the task entry point, not just chat.
- Keep one authoritative source per fact or status and link from elsewhere. Distinguish current specifications, unimplemented plans, and history, as well as implementation, verification, publication, and runtime acceptance. Report unverified work; partial checks or one successful run do not establish full completion. Historical cases do not override current specifications.
- Keep code and affected documentation consistent and check relevant links, commands, and status before completion. Documentation sync does not authorize additional operations or permit credentials and internal records in public artifacts.
