# Development Documentation and Task Continuity

- Development projects that require ongoing maintenance or cross-session handoff, and that involve any of multi-module collaboration, external services or deployment, phased delivery, or complex business constraints, should establish and continuously maintain five Markdown documentation responsibilities: README, SPEC, CHANGELOG, TASK, and CASE-STUDY. One-off, clearly scoped small changes do not need to complete the entire set for formality; when an existing project meets the conditions above, fill in the necessary documents during the related development task.
- First inspect the existing directory and documentation, and reuse files or sections that already carry the same responsibilities; follow the project's naming, capitalization, and language conventions. When there is no equivalent entry point, use `README.md`, `SPEC.md`, `CHANGELOG.md`, `TASK.md`, and `CASE-STUDY.md`. The root README provides navigation, while the other documents belong in the existing documentation directory; split them by responsibility in multi-module projects and link to shared rules.
- README explains the project's purpose, entry points, directory responsibilities, required configuration, usage and maintenance procedures, and actual build, verification, and deployment commands, so that a successor can begin work; link to the detailed specification and history instead of duplicating them.
- SPEC maintains the currently effective scope, behavior, interfaces and data contracts, key constraints, and acceptance criteria. Proposed designs and approved-but-unimplemented goals must be clearly distinguished from the current implementation; mark superseded designs as retired with their replacement entry point, and do not leave them as default instructions.
- CHANGELOG records meaningful feature, behavior, interface, and operational-maintenance changes and their impact by date or version, distinguishing unreleased from released changes. Record the final change rather than chat, tool logs, or every trial; decide according to project convention whether purely internal adjustments need an entry.
- TASK is the unified entry point for the current task and unfinished work. Record the objective and scope, status, next steps, dependencies or blockers, decisions needed from the user, and completion criteria; identify owners when multiple people collaborate. Distinguish to do, in progress, blocked, awaiting verification, complete, deferred, and canceled work; organize by plan or module ownership and keep unrelated work out. An existing task table may remain the sole source of truth: TASK should link to it rather than maintain duplicate status.
- CASE-STUDY records only real failures, rework, or erroneous judgments with reusable value. Record the symptoms and impact, evidence, confirmed root cause or unconfirmed hypothesis, ineffective attempts, fix and verification results, applicable boundaries, and lessons that prevent recurrence. When there are no real cases, say so instead of inventing one; as the content grows, use an index with separate linked records.
- When starting or resuming a task, read the specifications, operating instructions, current task, and existing related cases that apply to its scope. When requirements, implementation status, or acceptance conclusions change, update the corresponding documents in the same task; before ending, pausing, or handing off, write unfinished items, blockers, and next steps back to the unified entry point instead of leaving them only in chat.
- Base status on evidence that can be verified in the current round, and state implementation, verification, publication, and actual runtime acceptance separately. Partial tests, a save-and-readback check, or one successful run cannot replace an unperformed end-to-end or long-running acceptance test; report unverified parts honestly and do not trigger unauthorized operations just to mark work complete.
- Keep one clear source for current rules, current task status, and historical evidence; have other documents link to it. Historical cases' old versions, counts, statuses, and hypotheses must not override the current specification; promote lessons into the applicable specification, maintenance guidance, or rule only when evidence supports them and they remain applicable.
- Keep documentation and code consistent within the same task, updating only affected content; do not rewrite all five document types for every change. Before completion, check relevant links, commands, status, and actual results; follow existing publication and privacy boundaries so that internal tasks, failure records, and credentials do not enter public pages or public artifacts through documentation synchronization.
